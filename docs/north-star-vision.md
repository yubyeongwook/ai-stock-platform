# 북극성 비전 — AI Growth OS / 구독형 SaaS (최종 목표는 확정, 착수 시점만 보류)

**최종 목표는 구독형 SaaS로 확정됐다** (7절) — 사장님이 직접 가입·구독하면 그 티어에 맞는 마케팅이 자동으로 돌아가는 형태. 다만 **지금 당장 짓는 건 아니다.** 지금 우리는 1인 + 9개 에이전트로 Phase 0 파일럿을 준비하는 단계이고(`docs/marketing-agent-plan.md`), 이 문서의 나머지는 고객사가 6곳을 넘어 대시보드가 필요해지는 시점(Phase 2 이후)에 다시 꺼내 쓸 청사진이다. 지금 이걸 짓기 시작하면 매출이 나기 전에 몇 달을 엔지니어링에 쏟게 되어, Phase 0을 수동·린하게 시작하기로 한 이유(사례부터 만들자)와 정면으로 충돌한다 — Phase 0~3은 이 SaaS로 가기 위한 검증 단계이지, 별개의 목적지가 아니다.

이 비전의 초안은 사장님이 별도로 정리해 공유한 것을 바탕으로 정리했다. 안에 인용된 법 조문(공인노무사법 제27조의2, 의료법상 의료광고 규제, 치과의료광고심의위원회 등)은 방향은 맞지만 **정확한 현행 조문·적용 범위는 검증하지 않았다** — 실제로 컴플라이언스 로직을 짤 때는 반드시 변호사·노무사 확인을 거칠 것.

## 1. 최종 모습 — AI Growth OS

업체가 우리에게 주는 건 "업체 정보와 접속 권한" 하나뿐이고, 시스템이 고객 획득 → 전환 → 유지까지 자동으로 운영한다는 컨셉. "신규고객만 데려오는 회사"가 아니라 "한 명이 여러 번 돈을 쓰게 만드는 회사"가 지향점.

핵심 매출 공식(우리 문서에 이미 반영함, `docs/client-revenue-funnel.md` 참고):
```
매출 = 유입 × 전환율 × 객단가 × 재방문율 × 추천율
```
신규 고객 늘리기보다 **재방문율을 올리는 쪽이 광고비 추가 없이 매출을 늘린다**는 것이 이 비전의 핵심 통찰이고, 이건 우리 `revenue-model.md`의 "루프 3(리텐션)"과 정확히 같은 논리다.

## 2. Master AI + 12개 에이전트 (지금 우리 9개와의 관계)

원안의 12개 역할과 지금 우리 9개 에이전트는 상당 부분 겹친다:

| 원안 | 지금 우리 |
|---|---|
| CEO Agent, Business Analyst | 지금은 사람(나)이 직접 함 — 고객 수가 늘어야 분리할 가치가 생김 |
| Customer Agent, Competitor Agent | 아직 없음 — 온보딩 브리프에서 사람이 수동으로 파악 |
| SEO Agent | 블로그 최적화 + 로컬 SEO 에이전트 |
| Content Agent | 블로그 콘텐츠 에이전트 |
| SNS Agent | 없음 (릴스/숏폼은 촬영이 껴서 보류 결정함, 이전 대화 참고) |
| Ads Agent | 메타 광고 운영 에이전트 |
| CRM Agent | 리뷰·리텐션 에이전트가 일부 담당 |
| Conversion Agent | 랜딩페이지 카피 + CRO 에이전트 |
| Retention Agent | 리뷰·리텐션 에이전트 |
| Analytics Agent | 성과 분석 에이전트 |
| (Master) | 오케스트레이터 에이전트 |

**결론**: 지금 없는 건 Business Analyst/Customer/Competitor Agent — 즉 "업체를 분석해서 이번 달 우선순위를 스스로 판단하는" 상위 판단 레이어다. 이게 원안에서 가장 가치 있는 차별화 지점이고(치과 예시: "문제는 방문자 부족이 아니라 임플란트 상담 전환율이다"), 고객사가 늘어 성과 데이터가 쌓이면 이 판단 레이어부터 추가하는 게 순서상 맞다 — 데이터 없이 만들면 그냥 그럴듯한 대시보드일 뿐이다.

## 3. 공통 코어 + 업종 모듈 아키텍처

이미 `marketing-agent-plan.md`에 반영함: 코어(9개 에이전트)는 모든 업종 공통, 업종별로 달라지는 건 금지어·톤·컴플라이언스 체크리스트뿐이라는 원칙. 원안의 "업체 DNA 생성 → 업종 자동 판별 → 업종별 전략 엔진" 개념은 SaaS 단계(고객이 직접 가입하는 셀프서비스)에서나 필요한 자동화이고, 지금처럼 내가 직접 온보딩하는 단계에서는 사람이 업종을 보고 판단하면 충분하다.

## 4. 업종 확장 순서 (변경됨)

원안은 "의료는 규제가 강하니 나중에, 음식점+노무법인부터"를 제안했고 우리도 이를 채택했다(이전 버전의 "병원부터, 해자 우선" 결정을 뒤집음). 이유: 코어 엔진을 규제 부담 없이 먼저 검증하는 게 실행 리스크가 낮다. 병원·의료가 주는 해자(진입장벽)는 여전히 유효한 이점이라 Phase 3 이후 확장 대상으로 남겨둔다.

확장 우선순위 후보(코어가 검증된 뒤): 미용실, 피부과·한의원, 학원, 변호사·세무사, 부동산, 헬스장 — 각각 정도의 차이는 있지만 전문직/규제 업종은 노무법인과 마찬가지로 "성과 연동 가격을 못 쓴다" 같은 제약이 있을 수 있으니, 새 업종을 추가할 때마다 `competitive-moat.md` 4절 같은 검토를 먼저 한다.

## 5. 3단계 자동화 레벨

이미 `marketing-agent-plan.md` 5절에 표로 반영함(레벨1 완전자동/레벨2 AI생성+승인/레벨3 사람필수). 원안의 형식화가 우리가 흩어놓았던 Human QA 게이트보다 명확해서 그대로 채택.

## 6. 5개 매출 엔진 (참고용 프레이밍)

원안이 제시한 "엔진" 분류는 우리 9개 에이전트를 기능별로 다시 묶어본 것에 가깝다 — 새로운 실행 항목이 생기는 건 아니지만, 고객에게 설명할 때는 이 프레이밍이 "에이전트가 뭘 하는지"보다 이해시키기 쉬울 수 있다.

- 엔진 1 신규 유입: SEO+광고+콘텐츠+지도 = 블로그·로컬SEO·메타 라인
- 엔진 2 전환: 랜딩페이지+상담+예약+CTA = 랜딩페이지·CRO 라인
- 엔진 3 재방문: CRM+자동알림+개인화 = 리뷰·리텐션 라인
- 엔진 4 객단가 증가: 업셀+패키지+추가서비스 = 아직 담당 에이전트 없음, 고객 데이터가 쌓여야 의미 있는 제안이 나옴
- 엔진 5 추천: 리뷰+소개+추천 프로그램 = 리뷰·리텐션 라인

## 7. 최종 목표는 구독형 SaaS다 (확정)

Phase 0~3(지금의 1인 에이전시 모델)은 목적지가 아니라 **이 SaaS를 만들기 전에 코어 엔진과 업종 플레이북을 고객 돈으로 검증하는 단계**다. 목표 사용자 경험: 사장님이 업체 정보를 입력하고 구독 티어를 고르면, 그 순간부터 내가 매 고객마다 손대지 않아도 티어에 맞는 마케팅이 자동으로 돌아간다.

### 지금 이게 100% 자동은 안 되는 이유 — 정직하게 짚고 간다

"구독만 하면 전부 자동"이 되려면 모든 발행 단계가 API로 뚫려 있어야 한다. 지금까지 확인한 바로는:

- **카카오 알림톡·메타 광고·GA4**: 구독자가 자기 계정을 OAuth로 연결하면 완전 자동 실행 가능 — 멀티테넌트 SaaS 구조에 바로 맞는다
- **네이버 블로그 발행·스마트플레이스 수정**: 공식 퍼블릭 API가 없다(`marketing-agent-plan.md` 8절에서 이미 확인). **이게 "완전 자동 SaaS"의 가장 큰 병목이다.**

이 병목을 푸는 방법은 세 가지이고, 어느 걸 고를지는 사장님이 정할 문제다:

1. **원클릭 승인형(권장)**: 시스템이 초안을 만들고 구독자 본인이 앱 안에서 "발행" 버튼만 누름. 네이버 로그인은 구독자 본인 계정으로 하니 ToS 리스크가 없다 — 완전 무인은 아니지만, 사람 손이 "대행사 직원"에서 "구독자 본인의 클릭 한 번"으로 옮겨가는 것뿐이라 체감상 거의 자동이다
2. **브라우저 자동화**: 네이버 계정에 대신 로그인해 자동 발행 — 기술적으로는 가능하지만 네이버 이용약관 위반 소지가 있고, 계정 정지 리스크를 구독자가 떠안는다. **권장 안 함**
3. **자체 블로그를 기본값으로**: 우리가 완전히 API로 통제 가능한 자체 도메인 블로그(워드프레스 등)를 기본 제공하고, 네이버 블로그는 "추가 권장 채널"로 안내만 하되 발행은 구독자가 직접

**권장 조합**: 1번(원클릭 승인) + 3번(자체 블로그 기본 제공). "구독 = 100% 무인 자동"은 네이버 쪽 때문에 지금은 약속할 수 없고, "구독 = 내가 아니라 구독자 본인이 앱 안에서 버튼만 누르면 끝"이 지금 정직하게 팔 수 있는 선이다.

### 구독 티어별 자동화 범위 (초안 — 가격은 파일럿 검증 후 재산정)

| 티어 | 자동화 범위 | 필요 연동 |
|---|---|---|
| Basic | 블로그·플레이스 초안 자동 생성 + 원클릭 발행 | 없음(콘텐츠 생성만) |
| Growth | Basic + 카카오 리텐션 메시지 자동 발송 | 카카오 알림톡 연동 |
| Performance | Growth + 메타 리타겟팅 자동 운영 + 주간 성과 리포트 | 메타 비즈니스 + GA4 연동 |

### 지금 코드가 이미 이 구조로 짜여 있다

`orchestrator.py`가 고객사를 `clients/*.json` 파일 하나짜리 "테넌트"로 다루고, `integrations/`가 이미 카카오·메타·GA4를 크리덴셜 기반으로 분리해뒀다. SaaS로 갈 때 이 구조를 갈아엎는 게 아니라, `clients/*.json`을 멀티테넌트 DB 레코드로, 크리덴셜을 구독자별 OAuth 토큰으로 바꾸기만 하면 된다. 지금 파일럿에서 쌓는 업종 플레이북·콘텐츠 품질 기준이 이 SaaS의 실제 상품 경쟁력이 된다 — 그래서 Phase 0을 건너뛰지 않는 것.

대시보드 화면 구성(이번달 매출/신규고객/재방문/광고비/ROAS/CAC/LTV/AI 추천 액션 리스트)은 `marketing-agent-plan.md` 6절의 트리거가 오면(고객 6곳+) 그때 만들 화면의 초안으로 그대로 쓴다.

## 8. 채택하지 않는 것 / 보류하는 것

- **n8n/Make 중심 자동화 오케스트레이션**: 지금 오케스트레이터는 사람(나) + `orchestrator.py`로 충분하다. 실제 워크플로 자동화 툴은 반복 작업량이 사람이 못 버틸 정도로 늘어난 뒤에 검토
- **업체 DNA 자동 분류기**: 셀프서비스 가입 SaaS가 될 때나 필요. 지금은 온보딩할 때 사람이 업종을 알고 시작함
- **BASIC/GROWTH/PERFORMANCE/ENTERPRISE 4단계 정가제**: 방향은 참고할 만하지만 실제 단가는 `docs/revenue-model.md`의 파일럿 검증 결과로 다시 잡는다 — 지금 이 숫자들은 검증 안 된 가정치다
